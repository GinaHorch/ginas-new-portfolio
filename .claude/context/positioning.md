# Positioning & Messaging Direction

> **Purpose:** This document is the source of truth for portfolio messaging. Any agent touching homepage, About, Skills, project summaries, page titles, metadata, or SEO copy must read this before drafting.

## Core positioning

**Primary positioning statement:**

**TypeScript and full-stack developer building and improving production applications with AI-assisted engineering, security and systems thinking.**

The portfolio is moving away from a **"Scrum Master / career pivot into tech"** narrative. That background remains useful context, but it is no longer the headline.

Do not position Gina simply as an "AI Engineer" or imply machine-learning/model-development expertise that the portfolio does not demonstrate. Prefer:

- AI-assisted engineering
- AI-assisted software development
- AI-augmented development
- agent-assisted development
- context-aware AI development workflows

The differentiator is not simply that Gina uses AI coding tools. The stronger message is that she uses AI within disciplined engineering workflows: providing context and constraints, reviewing generated work, testing behaviour, diagnosing failures, preserving lessons, and remaining responsible for the finished system.

## Project proof points

Each featured project should demonstrate a distinct engineering capability rather than repeating "I built an app with AI."

- **Andromedae:** I can engineer, secure and ship a commercial production website.
- **She Codes Data Platform:** I can work inside a complex data platform and reason about integrations, identity, permissions, data integrity and security.
- **Wedding Guestbook & Media Platform:** I can turn someone else's professional design into a complete full-stack application, deploy it for real users, and hand the client independent control over their own private content.
- **Hold My Spoon:** I can inherit an existing product, understand it, diagnose problems, work across APIs/integrations, and continue developing it.

## Primary audience

The portfolio serves two overlapping audiences, in this order:

1. **Hiring managers and recruiters** for software development roles, including TypeScript, React, frontend/full-stack, data/platform, integration, and development roles where security or systems experience is valuable.
2. **Potential clients and collaborators** who need evidence that Gina can build, deploy, improve and maintain real software and work effectively with designers, stakeholders and existing systems.

## AI-assisted engineering direction

AI-assisted development should be a visible theme across the portfolio, but it should be presented as a way of engineering rather than a list of tools.

Current tools include:

- Claude Code
- Cursor
- Replit
- GitHub Copilot

Relevant practices include:

- persistent project context
- `CLAUDE.md`
- reusable skills
- project instructions
- Definition of Done
- planning before implementation
- code review
- verification
- debugging
- agent-assisted implementation
- iterative development
- preserving lessons from failed or imperfect runs
- updating project instructions so known mistakes are less likely to recur

Where appropriate, prefer **context engineering + review + verification** over generic "prompt engineering" language.

Do not claim that AI tools independently built the projects. Gina remains responsible for requirements, technical decisions, review, testing, security considerations and acceptance of the finished work.

## Agile and collaborative ways of working

Agile should **not disappear from Gina's professional story**, but it should no longer be presented as her primary identity.

The `/agile` Agile Resources section is being removed. Agile philosophy should instead appear as part of Gina's way of working, consistent with `.claude/GOAL.md`:

- collaboration over silos
- short feedback loops
- iterative improvement
- transparency
- continuous learning
- responding to evidence
- stakeholder feedback
- shared ownership
- clear Definition of Done
- reviewing outcomes rather than assuming implementation equals completion

Relevant terms such as Agile, Scrum, SAFe and Kanban may remain where they accurately describe experience, but they should not dominate hero copy, metadata, certification displays, or primary project messaging.

Prefer framing such as:

> **I use collaborative, iterative ways of working to build better software.**

## Tone and case-study style

Use a tone that is:

- professional
- technically credible
- direct
- human
- curious
- collaborative
- evidence-based

Prefer case-study language over marketing hype.

Project case studies should generally follow:

1. Problem / context
2. My role
3. Technical approach
4. Interesting challenge
5. AI-assisted workflow
6. Security / data considerations where relevant
7. Outcome
8. What I learned / improved

STAR principles may inform the structure, but pages should not read like interview answers labelled Situation / Task / Action / Result.

## Ownership and accuracy guardrails

Agents must preserve accurate project ownership:

- **Andromedae:** Gina is responsible for technical implementation and production delivery; visual design direction originated in Figma/design work supplied to the project.
- **Hold My Spoon:** Gina did not originate the product or build the original codebase from scratch; she inherited a partially developed application and substantially extended, debugged, integrated and supported it.
- **She Codes Data Platform:** Gina developed and maintained significant parts of an organisational platform; private data and internal organisational issues must not be exposed.
- **Wedding Guestbook:** Bianca Di Biase is credited for design and visual identity; Gina is credited for development and technical implementation.

Do not invent technologies, metrics, outcomes, responsibilities, seniority or design ownership.

## `/agile` direction

The `/agile` Agile Resources section is to be **removed**, not reframed as a standalone route.

Useful Agile philosophy should be retained within About and/or Skills as collaborative ways of working. Scrum-specific resource content and Scrum Master-heavy positioning should not remain as a central portfolio feature.

## About page direction

The About page should explain the unconventional career path without making it the site's central proposition.

A suitable narrative is:

**investigation → research/problem solving → technology → software development**

The investigation background may support strengths such as structured investigation, evidence assessment, risk thinking, stakeholder communication, persistence, documentation, privacy awareness, security mindset and complex problem solving.

The career history should explain **why Gina approaches technical problems the way she does today**.

## Metadata direction

Prefer titles such as:

**Gina Horch | TypeScript & Full-Stack Developer**

or:

**Gina Horch | Software Developer · TypeScript · React · AI-Assisted Engineering**

Metadata descriptions should mention a selection of TypeScript, React, full-stack development, production applications, AI-assisted engineering, APIs/integrations and cyber security.

Do not use "Scrum Master" in the primary site title or homepage meta description.

## Portfolio success test

Before approving new homepage, About or project copy, ask:

- Within 10 seconds, would a recruiter understand that Gina currently develops software?
- Does the portfolio show evidence of production work rather than only training projects?
- Does AI appear as an engineering workflow rather than a gimmick?
- Are TypeScript, React/full-stack capability and real applications clearly visible?
- Does cyber security strengthen the development story without overwhelming it?
- Is Agile visible as a collaborative way of working rather than the primary identity?
- Are claims accurate about what Gina built, inherited, designed or collaborated on?

If not, revise.
